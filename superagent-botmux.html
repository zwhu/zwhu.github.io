从 botmux 到持续任务协调：先验证续办收益

2026-11-01 · Agent 架构 · 源码研究

Super-agent 给研发工具的启发，是把需求、执行、评审与结果关联为一项持续任务。对于已经使用 botmux 的团队，值得先验证的是：自动把后续事件送回原执行者，能否减少人工转发与追问。

本文比较 botmux 公开版 v3.55.0 与 Super-agent 原型 6337fc8，不代表所有内部部署。以下是方案建议，尚未实施；公司规模、业务基线和实际收益没有提供。

1. 复用已有能力，补任务关联

工作 botmux 公开实现 Super-agent 公开实现
并行执行 按会话锚点与 bot 找到独立 CLI/Worker Ticket 对应独立 Worker 会话与目录
后续消息 按话题或群的明确锚点路由 Thread 与 Ticket 订阅，关联 PR 后直通
协调 bot 按编排技能派发与回报，也有 workflow 主会话判断请求与任务的关系
状态与恢复 持久会话、进程监督、冷恢复等 Ticket/Assignment、Effects/Outbox 与恢复路径
人需要介入 attention、@ 规则与决策看板 结构化问题、结果与原讨论回复

botmux 已有接入、执行和恢复功能。新增工程应集中在跨信道任务身份、后续事件关联和交付证据。话题锚点能确定会话，但一个业务任务可能跨多个话题、PR 与 CI，二者不是同一个标识。

公司是否受协调问题制约，要先分清时间花在哪里：模型执行、环境等待、人的阅读操作，还是返工。任务协调不能补偿错误代码或不可用的测试环境。

2. 第一版限定一个仓库和任务类型

建议先选择 PR 评审跟进或 CI 修复。保存原请求、授权、Task ID、Thread/PR 关联、当前 Worker、等待原因与交付证据。已明确归属的事件直接投递，关联不明时才交给模型判断。

先验证一条流程：请求 → 执行 → PR → 评审/CI 回到原 Worker → 提交验收证据。复用现有会话、消息和看板，不同时建设全公司记忆或扩大主动执行范围。

多个任务改动同一文件，需要额外的重叠检查和协调。单机事务能保证记录完整，不能保证模型没有重复建任务，也不能保证两个 PR 的逻辑兼容。

3. 用真实对照决定是否扩大

以团队当前最好用的 botmux 工作流作基线。两组使用相同模型、工具权限、Worker 上限和相近难度的任务，记录失败与额外审查。

指标 回答的问题
每个验收通过任务的人工主动操作分钟 是否减少了转发、读消息与催办
合格率、返工与回归 自动续办是否降低质量
错路由、重复任务、停止后继续 任务关联与控制是否可靠
总完成耗时及长尾 是否缩短等待，还是把排队转移了
增量模型、维护与基础设施费用 收益是否值得投入

作者的合成实验显示调度长尾缩短，没有测人工分钟和真实代码质量。五次运行的 p95 也不足以作为公司的稳定服务承诺。

先量基线，再影子判断、回放故障与停止路径，最后做受控对照。是否扩大，应根据净人工操作、交付质量和实际增量费用决定。预算收益须使用真实参数，释放的时间也不自动等于现金节省。

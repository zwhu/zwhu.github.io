# 对话中的写作反馈

用户照常在对话中要求 AI 修改文字，AI 在同一轮完成改写与记录，无需额外说“记下来”。只处理当前文档的反馈，不主动翻查历史聊天或把已有 diff 猜成用户的修改。

## 何时记录

用户针对已有文稿纠正措辞、语气、行文结构或叙述方式时触发，例如“太 AI 味了”“这句太虚，直接说做什么”“别用这个词”“这里留个例子”。只要用户明确在纠正表达，即使没有解释原因，也先保存例子。

事实纠错、数据更新、技术方案调整和纯排版不自动归为写作偏好。只有 Git diff、无法判断修改者或修改意图时，不认定为用户反馈。用户要求只检查或不写文件时，将待记录内容随建议呈现。

## 同一轮怎么做

1. 改写前保存原句、文档路径／章节和用户的纠正原话；读取[个人写作偏好](./writing-preferences.md)。未拿到原句时注明缺失，不补造。
2. 按要求修改文稿，把前后例子和依据写入[修改记录](./writing-feedback-log.md)。原因采用用户原话；用户未说明就写“未说明”。AI 的解释另标为“AI 推测，待确认”，不作为已确认原因。
3. 区分反馈的效力：用户明确表达的偏好可以成立；AI 生成的改稿先标“已按要求修改，尚无用户评价”。沉默、话题切换或任务结束均不等于认可改稿。
4. 用户继续纠正同一处时，在原记录下补充后续版本、原话与评价，保留前面的修改过程；不把多次尝试当作多条独立偏好证据。
5. 将明确的长期偏好提炼到偏好文件，附适用范围与记录 ID。结尾简短说明本轮记录了什么；必要的追问可以合并，不逐句询问，也不阻塞已授权的修改。

## 哪些进入长期偏好

- 用户明确要求“以后都这样”“我习惯……”等跨本次文稿的规则，可直接提炼并保留原话证据。
- “这篇引言短一点”先作为本篇要求；重复出现的倾向可在修改记录中归纳为候选，用户确认后再加入长期偏好。
- 用户确认了 AI 对原因的解释时，更新原因来源；确认某个改稿只证明该例子得到认可，不自动扩大适用范围。
- 新反馈与已有偏好冲突时，当前明确要求优先。说明此次例外或更新范围，保留旧记录，不把单次选择升级成全局禁用词。

## 记录格式

每次独立反馈使用一个 ID：`WF-YYYYMMDD-NN`，日期按 Asia/Shanghai。

```markdown
## WF-YYYYMMDD-NN

- 文档与位置：相对路径及章节；无法确定时注明。
- 用户原话：逐字引用本轮纠正。
- 修改前：原句或段落。
- 修改后：按要求修改的句子或段落。
- 修改原因：用户明确说明的原因；否则填“未说明”。
- 原因来源：用户原话／用户确认的解释／未说明。
- AI 推测：可选，须标“待确认”。
- 适用范围：本处／本篇／用户明确的长期范围。
- 改稿状态：已按要求修改，尚无用户评价／用户明确认可／继续修改。
- 后续反馈：有新反馈时追加原话、版本与状态。
- 偏好关联：已提炼的偏好 ID；没有则留空。
```

后续写作先读精简的偏好文件，再按其中的链接读取相关例子，无需每次加载完整修改历史。这些记录用于后续上下文，不代表模型训练。

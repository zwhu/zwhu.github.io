主要区别

1. 将“先让功能工作”“整理实现”改为自然、具体的中文，保留三个阶段。

使用前

ub-mode 是 Bob 大叔给编码 Agent 写的一份 Skill，主要内容是一组工程规范和工作流程。它把工程实践组织成三个阶段：先让功能工作，再整理实现，最后遵守日常实践。

使用后

ub-mode 是 Bob 大叔为编码 Agent 编写的 Skill，包含工程规范和工作流程。它分为三个阶段：先完成功能，再整理代码，最后遵守日常实践要求。

2. 明确 Skill、门禁和比较对象的分工，用“耗时和代码改动”代替笼统的付出。

使用前

这份 Skill 告诉 Agent 应当怎样工作。实际的工程门禁则由 lint、测试等工具执行，根据检查结果决定能否交付。这次想测的是：给同一个 Agent 加上 ub-mode 和它要求的工具，最终修复能否获得额外收益，以及需要付出多少时间和改动。

使用后

Skill 规定 Agent 的工作方式，lint、测试等工程门禁执行检查、提供交付依据。我想比较的是：同一个 Agent 使用 ub-mode 和配套工具后，修复效果是否改善，耗时和代码改动如何变化。

3. 删除“多个模块配合”与“四个模块”之间的重复表述。

使用前

这项修复需要处理编译流程中多个模块的配合。官方参考修复涉及四个模块、134 行业务源码改动。

使用后

官方参考修复涉及四个编译模块、134 行业务源码改动。

4. 标题直接说明成本具体是什么。

使用前

3.2 大实验：独立业务验收全部通过，额外成本仍然存在

使用后

3.2 大实验：独立业务验收全部通过，耗时与改动增加

5. 将抽象的“提供区分度”改为直接说明比较结果。

使用前

重复代码对在两轮两组中都为零，没有提供区分度。

使用后

两轮实验中，A/C 检出的重复代码对都为零，这项指标没有分出差别。

6. 用“写成测试”“运行检查”等动词说明做法，保留独立检查、诊断反馈和人工审查。

使用前

我会优先把 lint、类型检查、测试和 CI 这些 LLM 外部的门禁能力搭好。能静态检查的规范写进 lint 和类型检查，业务行为和边界条件落成测试，修复后在独立流程中执行检查，保留输出与退出状态。Agent 可以调用工具、根据具体诊断继续修复，交付依据则来自实际检查结果和必要的人工审查。

使用后

我会优先搭好 lint、类型检查、测试和 CI 等 LLM 外部的门禁。将静态规范写进 lint 和类型检查，把业务行为和边界条件写成测试；修复后在独立流程中运行检查，保留输出与退出状态。Agent 可以调用工具，根据具体诊断继续修复；能否交付由实际检查结果和必要的人工审查决定。

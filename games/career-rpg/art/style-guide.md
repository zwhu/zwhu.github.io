## 当前视觉与操作约束

- 主角与 NPC 造型、头身比、脸部、衣色、描边、脚底锚点及像素语言以成品核对，不能用通用小人替代；修技术缺陷时仍保留辨识度。
- 维持南京五工位背景、桌椅尺度、细节密度和连通走道，不用通用房间换色凑场景。场所与人物为设定，没有历史照片依据时不宣称真实还原。
- 普通剧情保留发言者头部附近的 DOM 气泡与避让，旁白锚主角；系统暂停、重玩和存档异常可用常规弹层。不能用旧底部对白框覆盖新 UI。
- 黄色感叹号在电脑上方、醒目且轻缓浮动，减少动态偏好时停浮动；实际接取后消失。情绪和坐姿打字保留，最新坐姿／气泡最终视觉仍待复核。
- 全键盘要求方向键选择所有对话与菜单选项、Enter 确认、Esc 返回，并保留 Tab／Shift+Tab、E／Q／M 和既有快捷键。菜单与对白内不移动，一次或按住确认键不跨界面误触；全键盘16项专项与23步连续流程已有特定版本证据，整体体验和其他环境仍分开验收。

## 场景区分度（本轮反馈）

用户指出程序场景v1过于简化、缺少区分度。后续先确定每个场景的空间结构与主物件，再绘制：宿舍要体现住宿与学习，驿站要体现存储与分拣，配送小区要有室外建筑和通行路径。去掉名称后仍应能根据结构和关键物件区分用途。不能仅更换墙色、桌椅数量或同一房间道具摆位；文件小与数量齐全不作为视觉通过依据。v2目前只重画3张，保留待审状态。

## 场景还原

新场景制作前列出已确认经历、照片或参考、关键物件、空间关系、人物行为及缺口。不能靠办公室换色或替换标题凑场景，不擅自编造年份、建筑布局、事故根因、原话或个人贡献。南京绿衣同事显示名已确认为「费翔🐘」，不因此补写其真实外貌、职位或对白。

南京现有运行布局由 `web/scene-config.mjs` 定义，逻辑空间384×216；论坛、排查电脑、CTO、手册等映射以 Web README 和源码为准。早期设计地图和目标旧 inventory 不覆盖运行坐标。事故根因、代码、排查细节、原话和真实布局仍缺失；缺口影响的验收项明确保留，不以虚构谜题换取通过。

## 绘图与素材交付

1. 人物、表情与关键动作默认使用image_gen；本轮已授权清单内缺失人物。实际附南京成品作为参考，角色附正面／四向、行走或NPC图；只写风格名不算提供参考。无真人外貌依据时，明确作为游戏角色设定。
2. 保留已通过素材并优先复用；必须新画时列明保持／修改项、用途、尺寸、动作与参考优先级，完整登记原图、提示词、工具、版本与实际参考输入。
3. TraeX缺少image_gen调用能力时，记录素材ID、场景、参考、提示词、保持/修改项与输出位置，由Codex调用内置image_gen。环境物件允许Python／SVG／Canvas等程序绘制，按南京成品验收；人物纯程序绘制保持实验状态。通用方块或占位图不能当正式美术。
4. 已有图集不等于严格生产网格已通过。透明边缘、帧尺寸、四向／步态对齐、脚底与渗色及实机表现分别验；保留源图，不将运行时 alpha 裁取冒充精确16×24或固定调色板。当前站姿42～44、坐姿40逻辑像素是现有实现参数，最终坐姿视觉待验，不为套早期尺寸重设造型。

## 逐场景门禁

当前授权集中准备缺失人物设定和文档，完成后交付审阅，不接入游戏或扩场景。loop、TraeX旧全旅程目标与走路卡顿排查继续暂停；单次素材工作不恢复后台任务。

恢复后同时只制作一个场景，依次事实／布局核对、制作、自验、监督者独立验收、返修和复验。每20分钟巡检，每次报告场景、进度变化、验收结论、本轮处理与下一步，无变化也报告。完成当前阶段即停；失败或当期必验项未验证不得开始下个场景。监督者须明确记录通过版本及下一场景授权，不自行解释为获准扩展。

监督者按阶段核对成品参考与同版本实际截图、全景与主角/NPC局部、道具尺度和 UI，并实际验全键盘、碰撞、剧情、存档与对应技术门禁。只看概念图或静态输出不算游戏验收。本次无行为变更，只做合并静态检查，不冒充新一轮游戏验收。

作者、真实设备、真人试玩按[验收方案](../acceptance.md)独立执行，监督者不代签。当期必需证据缺失则记录未验证，不能因进度或耗时降低标准。

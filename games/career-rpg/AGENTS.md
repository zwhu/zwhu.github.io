# 一路写来：像素 RPG

本文件适用于 `games/career-rpg/` 及其子目录，在仓库根目录 [AGENTS.md](../../AGENTS.md) 的基础上补充游戏规则。维护博客页面与发布产物时仍遵守对应目录和站点生成规范。

## 当前交互要求（2026-11-07）

- [首批试玩反馈](./review/2026-11-07-hefei-playtest.md)、[踩坑记录](./pitfalls.md)与[开发准则](./development-rules.md)是后续修复依据，尚未全部落实到代码。与下方历史交互说明冲突时，以本节及最新 handoff 为准。
- 进入对话后，方向键选择可用按钮，Enter 确认；无选择按钮时 Enter 推进文字，末句后收起。普通对话和技能弹窗共用控制，不要求先鼠标点击或 Tab 聚焦；对话期间不移动角色，一次确认不跨页误触。
- 取消「稍作停留」暂停弹窗，以 localStorage 自动保存和恢复章节、位置、朝向、收集、对话等可恢复状态。失焦清输入并停止后台更新，回来自动接续；保留旧存档兼容及失败处理。
- 对话字体缩小并设置层级和上限，统一按钮外观、选中与确认行为。书架只展示书，自己的工位电脑承担电脑交互，不额外叠屏幕。
- 合肥开场文案、需求入口与冗余确认按首批反馈修改；jQuery 指定提示呈现获得技能书。保留未被要求修改的剧情与表现，修复后逐项核对反馈编号。

## 当前方案与授权（2026-11-05）

- 先读[技术方案](./technical-plan.md)与handoff顶部当前恢复点。人物、表情和关键动作采用image_gen；程序负责可复用环境与裁切/图集/压缩。保留原图、提示词及来源记录，运行版经对照验收后接入。
- 用户已授权先准备[全旅程人物清单](./art/character-roster.md)中的缺失角色；这是素材准备，不放行场景或恢复loop。已有人物优先复用，不重复生成。
- 当前桌面键盘游玩，浏览器作开发入口；H5发布、移动端、触控和弱网暂不实施，原生封装工具未定。旧网络预算与候选失败保留历史，不充当当前阻塞或记为通过。
- loop与TraeX后台任务暂停；只有明确单次任务可执行。走路卡顿未解决且暂停排查，不因更新文档或制作人物而恢复。
- 下文“仅合并”“不生成图片”和旧分工是此前阶段记录，与本节冲突时采用本节和最新handoff；质量、史实、键盘与独立验收要求继续有效。

## 开始工作

- 开发前读取[踩坑记录](./pitfalls.md)与[开发准则](./development-rules.md)。收到试玩问题后，在同一轮记录现象、原因、修复方案、验证与预防措施；原因未查明时标为待定位，不把推测记成事实。修复后更新原问题状态，并将可复用的预防动作补入准则。

- 制作方读取对应规格和交接并自检；监督者读摘要、差异和成果并独立验收。不要反复通读长日志或重复执行已完成检查。当前TraeX与loop暂停，保留会话现场。

- 先读 [handoff](./handoff.md) 确认当前阶段，再按任务读取 [规格](./spec.md) 与 [验收方案](./acceptance.md) 的相关章节。不要将设计提案当作已确认或已实现的功能。
- 南京完整样章及四向行走、NPC、情绪、坐姿打字和五工位已实现并合并；键盘、阅读和回退已有独立证据。完整场景未验收，卡顿排查暂停。当前授权文档更新及清单内缺失人物设定，不重做南京或接入新场景。
- 后续质量高于速度，同时只制作一个场景；读[美术规范](./art/style-guide.md)，自验后等待监督者独立验收。失败或当期必验项未验证不得进入下一场景；通过版本与下一场景授权必须明确记录，不把沉默当认可。
- 每20分钟监工当前明确暂停。单次素材或文档工作不会恢复调度；用户明确恢复后再按每轮报告的既有要求执行。
- 查看最新文件与 Git 差异，保留用户已有及无关修改。每完成一步、启动长调用之前或遇到阻塞时，立即更新 handoff 中的进度、验证证据、在途任务标识和唯一下一步，不等整轮结束。

## 项目边界

- 技术方向为 Three.js 加项目自用的简单引擎。引擎随南京样章的实际需要扩展，先不构建通用框架。
- 源码、素材、设计、测试和维护脚本集中于本子项目。原图与处理候选单独归档，运行依赖只引用已通过素材。博客首页、导航和文章列表不放游戏入口。
- 可玩副本由仓库根目录 `scripts/publish-career-rpg.py` 生成到 `docs/games/career-rpg/`，不手改发布资源。`python3 scripts/verify.py` 会核对这份副本。发布副本只含运行所需的页面、模块、图集和三份章节 JSON；测试、审阅材料和未使用的 Three.js 不进 `docs/`。游戏页保持 noindex，「回到博客」在副本里指向 `https://zwhu.github.io/`。
- 导出应可重复，提供同步检查；不手改发布资源，不导出概念稿、提示词、测试和工作文档。GitHub Pages 继续直接发布 `main /docs`。
- 游戏代码与资源仅在游戏页加载，不增加普通博客页面的游戏依赖请求。

## 美术与剧情

- 所有场景遵守用户确认的交互规范：对话气泡锚定发言人物头部附近；主角四向行走；场景中实际放置可交互的关键人物与同伴；办公场景有成组工位；电脑任务以黄色感叹号提示，接取后消失；人物支持紧张、开心等情绪表现。采用可复用场景配置和组件，不能只在南京临时实现。

- Codex负责image_gen调用、实际参考输入与最终视觉复核；TraeX获单次授权后可制作程序环境素材、处理脚本和游戏代码并自检。人物纯程序绘制仍为实验，默认人物生产走image_gen。

- 游戏画面使用用户指定的像素 RPG 风格，细节以规格中的美术方向为准；博客页面外壳沿用站点视觉规范。
- 美术基准是已实现的 `web/art/office-room-v2.png`、四向行走／NPC／情绪／打字图集及 `art/character-front-v1.png`、`character-four-directions-v1.png`。旧南京 v1 概念板仅辅助；早期 grid-sample 作者认为不好看，不作为正式造型。后续绘图实际附对应南京成品参考，不用旧概念覆盖已认可版本。
- 区分概念板与生产素材。生产素材统一像素网格、调色板、帧尺寸和脚底锚点；保留源文件、生成提示词或工具记录以及外部素材许可。
- 真实经历以规格中的事实表与用户后续纠正为准，不编造事故根因、年份、真人外貌、原话或个人贡献。新补充同步更新规格，避免与验收方案矛盾。
- 剧情文字和状态分开维护，以稳定事件 ID 连接；使用 HTML/CSS 呈现对话与菜单，保持中文清晰和键盘可用。

## 实现与验证

- 所有核心操作必须可仅用键盘完成；对话与菜单支持方向键选择、Enter确认、Esc返回，保留Tab／Shift+Tab、E／Q／M、可见焦点和恢复。对话内不移动，一次确认不跨界面误触。当前16项专项与23步连续流程已有特定版本独立证据，其他桌面环境和完整体验不自动通过。

- 验收先分责任，再分材料：Agent 完成当前阶段全部必验项并通过后，才能提交作者正式验收。图片与视频是审阅材料，不能代替技术检查；失败或未验证的必验项先自行解决。作者主要确认美术偏好、个人经历表达与体验，具体门禁见验收方案。
- 剧情状态可序列化，纯逻辑不依赖 DOM 或 Three.js；渲染不决定剧情。检查重复触发、跳过、读档、暂停和失焦时的状态一致性。
- 游戏循环避免每帧无谓计算与分配；管理场景资源释放。依赖固定版本并保留许可，体积和性能按验收方案实测。
- 发现问题先保留复现方式，修复后按需补回归测试、数据检查或可普遍检测的 lint 规则；保留解释真实陷阱的必要注释。
- 游戏检查实现后接入全仓 verify，不以文档中列出了检查代替实际执行。修改后从仓库根目录运行 `python3 scripts/verify.py`。
- 修复首批试玩问题后按[验证与交付](./regression-guide.md)运行浏览器 acceptance 回归，逐分支生成并审阅截图报告再交作者。baseline 仅用于旧版本取证；上游失败、旧按钮回退或未执行的分支不得标通过。截图与录屏默认存仓库外，检查窗口实际可见性，不只读 hidden 属性。
- 当前页面与交互按桌面范围实际预览；窄屏检查可用于开发，但移动端、触控和手机真机留待对应阶段，不将模拟结果写为真机通过。PR与站点发布另按根目录流程。
- 汇报区分自动检查、视觉审阅、实际交互和性能测量，未运行的项目明确标为未验证。不要以静态检查通过声称游戏可玩或性能达标。

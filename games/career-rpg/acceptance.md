# 《一路写来》验收方案

更新：2026-11-05。当前范围按[技术方案](./technical-plan.md)执行：桌面键盘游玩、image_gen人物与表情、程序环境素材、原图归档及压缩运行版。H5、移动端、触控、弱网与线上发布暂不实施；对应检查保留为后续阶段，不记通过。桌面原型的历史作者验收不覆盖完整场景和最新反馈。

对应 [规格](./spec.md) 与 [交接](./handoff.md)。美术方向确认、样章可玩、全旅程发布分别验收，不混称完成。

## 验收分层与交付顺序

南京主线和共用表现已合并，16项键盘专项与23步连续键盘旅程已有监督者独立证据。长对话、回退、规则和生命周期各按证据范围判断，详见交接；不能标作整个游戏通过。卡顿未解决且暂停排查，最新坐姿／气泡整体视觉、其他桌面环境和完整内存仍有未验项。loop保持暂停。

本阶段的可玩检查以桌面为范围；下文手机、触控及H5发布条目仅在恢复对应阶段后适用。浏览器保留为当前开发预览工具，桌面原生封装尚未选型。

场景门禁：质量高于速度，同时只制作一个场景；自验后停下等待监督者独立验收。失败或当期必验项未验证不得开始下个场景。监督者须明确记录通过版本和下一场景授权；作者、真机、真人试玩仍独立执行。恢复制作后每 20 分钟巡检且每次报告，无变化也报告，暂停期间不自动续作。

### 所有场景的共用表现检查

- 全键盘流程：不使用鼠标完成从进入场景、接取任务、选择附近对象、推进剧情到查看手册、暂停恢复、章节完成和重玩，覆盖存档异常提示。所有选项须方向键选择、Enter 确认、Esc 返回；保留 Tab／Shift+Tab、Enter／Space、E／Q／M 和其他已有快捷键、可见焦点与焦点恢复。对话与菜单内不移动角色，一次或按住确认键不跨界面误触。以实际浏览器键盘输入为证据，不用脚本调用按钮或状态函数替代。

- 对话气泡跟随发言者头部，靠边可避让，不遮挡关键角色或跑出画布；暂停等系统确认可保留普通对话框。
- 移动方向与前后左右造型一致，停下恢复站立，走动使用对应方向的步态；不把正面图平移当成四向走动。
- 关键人物和同伴在场，可接近交互，交互对象清楚；办公场景有多组工位及连续走道，碰撞与画面一致。
- 黄色感叹号只提示可接电脑任务；接取后消失，靠近或预览不误消失，刷新和重玩保持正确状态。
- 紧张、开心等表情由剧情驱动，角色/对话中的变化可辨，不只在测试数据中存在。

以上为用户对后续所有场景的要求，南京本轮落实后应保留为共用回归检查。仍先执行桌面 Web 验收。

2026-11-04 用户调整实施顺序：先交付可在桌面浏览器实际运行的 Web 原型，验移动、碰撞、交互、暂停与失焦；移动端、真机和其他端验收在 Web 跑通后执行，不阻塞本阶段。Web 原型不等于可玩样章或正式发布，后续阶段仍按对应标准检查。

每个阶段遵循：开发与制作 → Agent 验收 → 全部通过 → 作者验收 → 修改后重新验收。图片与视频是验收材料，责任按下面两层划分。

### 第一层：Agent 验收

Agent 先核对当前阶段交付范围，执行对应的自动检查与人工复核，发现问题自行修复。不能只运行 verify 就将浏览器、视觉或交互检查标为通过。

| 阶段 | Agent 必须先验什么 | 通过后交给作者什么 |
| --- | --- | --- |
| 章设计资料 | Flash 自检后由 Codex 独立核对已知事实、地图、剧情条件、存档规则和美术规格一致性；保留实际调用及检查证据 | 设计稿、美术制作规格、结构化数据及监督记录；只确认叙事与设计方向，不代表游戏验收 |
| 美术方向 | 概念图符合本轮视角、配色、角色和构图要求；文字无明显错误；标清设定与事实、概念稿与生产素材；没有影响本轮判断的已知缺陷 | 已自检的概念图、本轮确认范围和简短自检结论 |
| 生产美术 | 像素网格、透明边缘、图集、方向与帧对齐符合规格；实际渲染显示正确；素材来源可追溯 | 实机截图和必要动画片段 |
| 可玩样章（当前桌面阶段） | verify、完整剧情、键盘输入碰撞、暂停与存档恢复、桌面布局、素材加载和当期运行检查通过；核对文案与已提供事实一致 | 同版本截图、实际录屏、试玩入口及自验报告；手机和弱网分阶段列明 |
| 正式发布 | 全旅程、部署产物同步、导航与后备阅读、设备与性能、站点回归和发布前检查通过 | 完整旅程材料、发布候选版本及自验报告 |

门禁规则：本阶段必验项只要存在失败或未验证，就不进入作者正式验收。缺少设备或证据时，先解决或如实报告阻塞；不能让作者承担技术排查。若确需缩小阶段范围，须先取得作者明确同意并记录，不能默默降级标准。

未来阶段的检查不阻塞当前阶段，例如概念图无需先满足游戏帧率。它们记录为“不适用（未进入该阶段）”，不能写成“通过”。内部进度展示可以包含草稿，但必须标为未通过自验，不要求作者给出验收结论。

### 第二层：作者验收

作者只在 Agent 当前阶段验收通过后参与，主要判断个人偏好、经历表达与最终体验。Agent 不替作者确认这些结论。

| 作者判断 | 主要依据 | Agent 提前负责 |
| --- | --- | --- |
| 美术是否喜欢、人物是否有自己的感觉 | 已自检的图片与动画片段 | 网格、显示、帧对齐、布局和文字可读性 |
| 经历是否准确、语气与情绪是否符合本人 | 剧情文字和完整样章录屏 | 先消除与已知事实矛盾、虚构根因和错误数字 |
| 探索是否有趣、节奏是否舒服、交互是否自然 | 实机录屏和短暂试玩 | 先消除卡关、功能故障、明显卡顿和设备适配问题 |
| 是否接受当前阶段、是否进入下一阶段 | 上述材料与修改对照 | 附自验结论、材料版本及本轮范围，不把沉默当认可 |

作者正常使用时仍可能发现新问题，Agent 负责复现与修复，不要求作者提供根因。作者提出修改后，先重新执行受影响的 Agent 检查并通过，再提交作者复验；不因已获美术认可而跳过技术回归。

## 作者验收材料：图片与视频

以下材料只在本阶段 Agent 验收通过后正式提交。作者不必逐条阅读测试输出；交付时提供简明结论与可追溯证据。图片与视频分别记录通过、需修改或未验证，不能相互替代。

### 第一部分：图片验收

南京已实现版本及原图是本轮参考：五工位 `web/art/office-room-v2.png`、四向行走、NPC、情绪、坐姿打字图集与正面／四向设定，详见[美术规范](./art/style-guide.md)。已有 `web/review/` 实际截图，需按版本和范围判断；最新坐姿／气泡等最终视觉仍待验。旧概念板 v1 仅辅助，不因其缺陷重画成品；严格网格、透明边缘、调色板与最终实机效果继续各自验收。

样章实现后提交以下实际截图，标明版本、场景、视口与设备；同一批图片使用相同游戏版本：

| 图片 | 作者主要看什么 |
| --- | --- |
| 办公室全景与角色／道具局部 | 是否喜欢整体风格，角色是否清楚，像素颗粒与物体比例是否统一 |
| 对话框、论坛与工作手册 | 中文是否好读、文字是否准确，界面是否遮住关键内容 |
| 同场景桌面与手机竖屏 | 人物与交互点是否看得清，触控按钮和文字是否拥挤或被裁切 |
| 昼夜对照 | 场景之间风格是否一致，夜景是否仍看得清楚；相关场景实现后再交 |

作者反馈可直接写“第几张、哪里、希望怎么改”，例如“手机图里的字太小”“主角更成熟一点”“像素颗粒再粗一点”。美术方向由作者明确确认；未回复不视为通过。PNG 保留原始尺寸，并注明 CSS 视口、DPR，避免缩图掩盖边缘问题。

### 第二部分：视频验收

提供实际浏览器录屏，用于检查走动、互动、动画、恢复与故事节奏。标明版本、浏览器、设备、分辨率及输入方式；不拿生成视频、剪辑宣传片或概念动画作为可玩证据。

| 视频 | 内容与作者主要判断 |
| --- | --- |
| 完整样章，预计 2～3 分钟 | 从进入办公室到手册新增记录，正常速度连续录制，不剪掉加载或卡住的片段；能否看懂下一步，剧情是否像自己的经历，等待与文字量是否舒服 |
| 桌面交互片段 | 走动、碰撞、靠近提示、打开和关闭对话、查看手册；是否跟手，动作是否自然，反馈是否清楚 |
| 手机交互片段 | 真机触控走动与对话，展示横竖屏切换；按钮是否好按，手指是否遮挡目标。模拟触控录像须标注，不替代真机验收 |
| 异常与恢复片段 | 连续点击、跳过、刷新继续、切后台再返回；能否继续推进，是否有残留移动或重复事件 |

作者按时间点反馈，例如“00:42 不知道要去哪里”“01:18 对话太快”“这句不是当时的意思”。操作录屏保持实际速度，保留必要的输入提示；若附加放大或慢放，单独标注，不替代原始片段。

### 如何决定是否通过

1. Agent 当前阶段全部必验项通过后，作者先看图片确认美术方向，再看实际样章的视频确认动态体验。图片方向需要大改时先修改，不批量扩展城市素材。
2. 作者确认风格、叙事与节奏；开发侧负责自动检查、设备与性能证据。视频不能证明触屏手感、输入延迟和帧耗时，正式样章验收仍提供可访问的试玩入口，作者在自己的设备上简单走一遍。
3. 会卡关、丢存档、触控不可用、史实错误的问题必须修复；风格与节奏修改附反馈，完成后提交同场景对照图或对应片段复验。
4. 每轮交付附一张结果表，分列 Agent 验收与作者验收，包含版本、阶段范围、逐项结论与证据、图片／视频路径、作者反馈和下一步。必验项未验证时保留在 Agent 层，不提交正式作者验收；概念方向通过不等于样章验收通过。

证据建议保存在子项目 `review/<版本>/`，大体积原始视频可以存于可访问的外部附件，并在结果表登记链接；不将审阅视频导出到游戏发布目录。实际提交前检查体积，不预先生成空目录或占位视频。

## 美术审阅

| ID | 检查 | 通过条件 |
| --- | --- | --- |
| ART-01 | 风格与场景 | 南京办公室读作可走动的 RPG 场景，走道与对象可辨，像素尺度一致；无柔焦、无混杂透视 |
| ART-02 | 主角 | 同一角色前后左右轮廓和服装一致，能与 NPC 区分；外观为设定，不宣称真人还原 |
| ART-03 | 三城与昼夜 | 宿舍、办公室、深夜书桌共用视觉语言，靠物件、环境与时间区分 |
| ART-04 | 文字与 UI | 对话框与像素画面协调，中文使用清晰字体；正式文字不烘焙进概念图 |
| ART-05 | 生产素材 | 后续素材严格按网格制作；帧尺寸、脚底锚点、透明边缘一致，无相邻图块渗色 |
| ART-06 | 用户审阅 | 记录用户对视角、人物、色彩和 UI 的明确反馈；概念板通过与 ART-05 分开确认 |
| ART-07 | 南京成品一致性 | 对照已实现五工位背景、正面／四向／行走、NPC、情绪、坐姿素材与同版本实际截图，核对造型、头身比、衣色、描边、家具尺度及头部气泡；不以旧概念或 grid-sample 替代成品，不以“都是像素风”判通过 |
| ART-08 | 场景还原与独立验收 | 事实、布局依据、关键物件及缺口可追溯，不用通用房间换色；当期必验项全过，监督者明确记录通过版本并另行授权下一场景；失败或缺证据不放行 |
| ART-09 | 原图与运行版本 | 原始输出、参考、提示词、来源信息保留；处理脚本、参数、帧尺寸/锚点和输入输出哈希可追溯，候选通过后才替换运行引用 |
| ART-10 | 压缩视觉与资源 | 无损候选核对解码RGBA、色彩和透明；缩放/量化等视觉变化做原图及南京同尺度对照，脸、发型、轮廓、衣色与动作保持；分别记录文件、解码缓冲及GPU观测，不按文件小判通过 |

概念阶段只验 ART-01～04、06；ART-05、09、10用于生产与处理后的运行素材。人物、表情和关键动作默认由image_gen参考现有成品制作；程序家具样品也需通过同样的风格检查。美术通过后，仍须实际渲染证明缩放、动作与遮挡正确。全旅程人物设定可先集中准备，场景接入和放行仍逐场执行。

当前范围调整：下表512 KiB/2 MiB和1 Mbps下8秒保留为此前H5目标；4 MiB/6 MiB/40秒仍是未批准候选。H5暂不实施，网络体积及弱网启动条目暂停作为当前桌面阶段的阻塞项，不将历史失败改写为通过，也不继续冷启动候选测试。人物素材照常压缩并记录文件与解码大小；桌面流畅性和资源释放要求保留，卡顿排查仍按用户指令暂停，未解决项不得放行。桌面原生包大小与设备性能数值在选定交付环境后另定。

| 项目 | 首版目标 | 方法 |
| --- | --- | --- |

| 受控启动 | 1 Mbps、150ms 请求延迟、冷缓存，3 次中位数不超过 8 秒达到可操作 | 本地记录导航开始到角色可响应输入；明确压缩与 CPU 设置，不当作真实手机结论 |
